Prompt (paraphrased)

A "ghost" that streams data between two processes. Recover the flag it whispers over its private channel.

Files provided

  • GhostStream.wim — a WIM image. Contains the parent executable (GhostStream.exe), supporting data, and (importantly) content in alternate data streams that a naive extraction misses.

Tools used

  • 7-Zip with -sns (extract NTFS alternate data streams from the WIM)
  • Ghidra (headless decompile) for the parent/child logic
  • Python (_winapi) to sniff the named pipe dynamically (sniff.py)
  • Custom Python to model the string decryptor (dec.py) and the modified RC4 (solve.py, brute.py)
  • A patched child binary (child_patched.exe) for controlled execution

Methodology

1. Extract the WIM (including ADS)

The WIM hides data in alternate data streams; extracting with 7z x -sns surfaces the extra files (e.g. PolyjuicePotion.txt) alongside GhostStream.exe.

2. Understand the architecture

GhostStream.exe (the parent) drops a child (Partner_CTF.exe) into %TEMP% and talks to it over a named pipe: \\.\pipe\FlareChallenge. The flag is transmitted across this channel.

  • To observe it live without fully trusting the sample, sniff.py pre-creates a lock on the child drop path, launches the parent with a redirected TEMP, then opens the pipe itself and reads the message.

3. Beat the obfuscation

Strings are encrypted with a sum-selected multi-mode scheme — the decryptor picks an operation (-k, (+1)^k, -2+k, …) based on the byte-sum of each blob and a key byte derived from the module name (dec.py reproduces the exact table).

4. The cipher: a modified RC4

The flag emitter is RC4 with a twist (solve.py): - KSA: standard j = j + key[i%len] + S[i]. - PRGA: the index step is i += 19 (not +1), and each keystream byte is additionally masked: out[k] = S[(S[i]+S[j])&0xff] ^ Dt[k] ^ ((19 + C[k]) & 0xff) where Dt is a string run through a patched strlen-style transform (s[i] = ((s[i]+i+1)&0xff) ^ 0x13) and C is a fixed 38-byte blob embedded in the child.

5. Recover the key & flag

The key material is themed (AlbusDumbledore, the Polyjuice Potion). We enumerated the plausible key candidates (potion text, the window-create message variants, AlbusDumbledore with/without trailing space) and the step value L ∈ {18,19}, ran them through the modified PRGA, and selected the output containing flare-on:

A Word document that is far more than it appears. Follow the trail of file formats to the treasure.

  • flareon13.doc — the polyglot. Simultaneously a DOS COM program, a Word doc, an ISO/UDF image, a ZIP (using the obsolete Reduce compression), a PDF, and a carrier for a Mach-O ARM64 binary.

  • PDF object extraction/decoder (pdfdec.py)
  • ISO 9660 / UDF parsing (udf)
  • Mach-O parsing + hashlib (MD5/SHA-256) + RC4 (final.py)

Methodology

This challenge is a nested "treasure hunt" — each format is a layer pointing at the next.

1. DOS COM stage

flareon13.doc begins with runnable 16-bit code. Emulating it in Unicorn (UC_MODE_16, load at 0x100, hook int 0x21 for AH=09h/02h output) prints the first clue and reveals how the file doubles as other formats.

2. Polyglot container layers

The same bytes parse as: - an ISO 9660 / UDF optical image (cd.iso, udf) — tagged descriptors carry a stage, - a ZIP archive whose entries use Reduce compression (method not supported by modern tooling → hand-rolled unreduce.py), - a PDF (objects extracted/decrypted in pdfdec.py, images img0.png / page_small.png).

Following these produces the final payload: a Mach-O ARM64 executable (macho/click_me~.arm64-3).

3. Final crypto in the Mach-O

The Mach-O embeds six themed string fragments, each validated by an MD5 stored (as nibble-packed bytes) in the binary:

FLARE-STANDARD-ANTIVIRUS-TEST-FILE!   (EICAR nod)
mainframe_ebcdic_ghost
jbig2_fax_geometry
udf_tagged_descriptor
reduce_not_deflate
Ød1n_373rn4l_fl4r3                    (Odin / "eternal flare")

The RC4 key = XOR of SHA-256(fragment) over all six fragments (32 bytes). The S-box seed is the identity permutation; a standard RC4 KSA/PRGA then decrypts the embedded ciphertext:

key = bytearray(32)
for f in frags:
    for i,c in enumerate(hashlib.sha256(f.encode()).digest()):
        key[i] ^= c
# standard RC4 KSA over identity S, PRGA, XOR ciphertext -> flag

Prompt (paraphrased)

A cryptominer that "melted your CPU" — recover what it was really computing. The flag is gated on your machine's identity.

Files provided

  • ToxicMiner.exe — a trojanized cpuminer-multi build. The mining code is a decoy; a hidden routine derives a key from the host and prints Accepted: <flag> only on the intended machine.

Working files: image.bin (the PE mapped image), harness.c/harness.exe (brute-force harness), emu_key.py / emu_comp.py, h_*.txt / hit_*.txt (brute-force shards), recover.c (pure-C reimplementation).

Tools used

  • Ghidra (headless) to locate the key-derivation (FUN_140134ca0) and RC4 (FUN_140134d70)
  • pefile to produce a flat mapped image (image.bin)
  • Image-mapping harness (harness.c): VirtualAlloc the PE at its preferred base 0x140000000 with PAGE_EXECUTE_READWRITE, then call the binary's own functions directly as function pointers — guaranteeing byte-exact (modified) SHA behavior without re-implementing it
  • A parallel pure-C reimplementation (recover.c) for cross-checking and speed

Methodology

1. Cut through the cpuminer noise

The bulk of the binary is legitimate cpuminer-multi. Static triage isolated a non-mining routine that reads the C: volume serial number and uses it as a seed.

2. The key derivation — a word-oriented SHA-256d

The key is a double SHA-256 (SHA-256d) implemented over uint32 word arrays (no input byte-swap), seeded by the volume serial and a magic constant 0x0b501e7e:

round1 W = { serial, 0x0b501e7e, 0x80000000, 0..., 0x40  }
H1 = SHA256_compress(IV, round1 W)
round2 W = { H1[0..7], 0x80000000, 0..., 0x100 }
H2 = SHA256_compress(IV, round2 W)
key = little-endian bytes of H2[0..3]        # 16-byte RC4 key

RC4 then decrypts a 0x33-byte blob; the plaintext is Accepted: <flag>.

3. Brute-force the volume serial (2^32)

A volume serial is a 32-bit value, so the whole space is brute-forceable. Two independent solvers were run and cross-checked:

  • recover.c — a from-scratch SHA-256d + RC4 in C, scanning serial ranges for a plaintext containing flare-on.com.
  • harness.c — maps image.bin at 0x140000000 and calls the binary's own FUN_140134ca0 (key) and FUN_140134d70 (RC4), so even a modified SHA is reproduced exactly. Work was sharded (h_*.txt / hit_*.txt) across ranges.

The winning volume serial = 0x01CEC01D (a cheeky "ICE COLD" / "01CEC01D") yields:

Prompt (paraphrased)

A cat burglar's implant exfiltrated some contraband. Reconstruct the heist from the executable and the packet capture and recover what was stolen.

Files provided

  • catthief/catthief.exe — PE32+ x86-64 Rust implant (implant.pdb); uses ureq/rustls/ring/flate2/miniz_oxide.
  • catthief/capture.pcapng — 6 POST /exfil requests + responses to the C2.

Solver: 5-catthief/decoder.py (+ recovered images in 5-catthief/recovered/).

Tools used

  • Ghidra (headless) to reverse the exfil routine and identify RC4 (KSA FUN_1400052e2, PRGA FUN_140005281) and the custom compress.rs
  • Frida 16.5.9 as a compression oracle — redirect connect→local C2 and CreateFileW→known probe files, replay the real pcap commands, feed inputs with known byte-frequencies
  • Python for the RC4/Huffman decoder; Pillow to render the recovered JPEGs
  • Defender evasion: extract to memory with 7z e -so + patch a DOS-stub byte to change the file hash before detonation

Methodology

1. Map the protocol

The implant reads a target file, custom-Huffman-compresses it, RC4-encrypts it, and POSTs to /exfil. Responses carry the next file path command. The pcap holds 5 exfiltrated JPEGs (plus a READY beacon).

2. RC4 layer

The cipher is standard RC4 with a 25-byte key decoded in-binary via ^0x33:

key = b"i11_b3_p1und3r1n_y3r_d474"   # "ill be plunderin yer data" (pirate speak)

The keystream is reused from position 0 for every message — decrypting the pcap response bodies yields clean Windows file paths, confirming the key.

3. The custom Huffman format (the hard part)

catthief ships its own compress.rs (not flate2). After RC4 decryption each message is:

Region Meaning
byte 0 magic 0x20
bytes 1..262 a big-endian integer; the 256-entry code-length table = int.from_bytes(pt[1:262],'big') >> 5 (base-256 digits → length[symbol])
from bit 2091 Huffman bitstream, read MSB-first, standard canonical codes (sort by (length, symbol))

The >>5 (×32) storage is why all-length-8 files show the telltale 01 01 01 … header. Validated by the Kraft equality Σ 2^-len == 1.000000 on every real capture.

# core of decoder.py
def parse_lengths(pt):
    T = int.from_bytes(pt[1:262], 'big'); L = T >> 5
    lb = L.to_bytes(261, 'big')
    return [lb[s+5] for s in range(256)]

def canonical(lengths):               # standard canonical Huffman
    syms = sorted((lengths[s], s) for s in range(256) if lengths[s] > 0)
    codes = {}; code = 0; prev = 0
    for l, s in syms:
        code <<= (l - prev); codes[s] = (code, l); code += 1; prev = l
    return codes
# decode MSB-first from bit 2091 until EOI (ff d9)

4. Cracking the format with a compression oracle

The table serialization and the constant bit-2091 data offset were reverse-engineered empirically: under Frida we fed the implant tiny inputs with known byte frequencies (e.g. [10,11,…,17] → all length-3) and read back the exact code assignment, proving the codes are plain canonical and pinning the data start.

5. Recover the loot

All 5 messages decoded to valid JPEGs (SOI ffd8ffe0 → EOI ffd9), 2816×1536 pirate cats. The flag is painted on a scroll on the treasure chest in catcatcat.jpg:

Files

  • challenge.pcapng — 966 packets, one TCP/80 conversation (192.168.198.129 ↔ mock 192.168.198.130, Server: MockHighscore/1.0).

TL;DR

The game's managed code is a faithful decoy. The exe ships a modified .NET runtime (a custom‑built CoreCLR statically linked into the apphost, reporting a fake version 42.42.42.42424). At startup it installs MinHook‑style detours on a handful of managed methods. The EncodeFeedbackBuffer detour secretly exfiltrates the stdout of a local updater.exe through the telemetry feedback_b64 field, XOR‑encrypted with a PCG/LCG keystream whose seed is the machine's MachineGuid. Because the covert feedback_length and a 16‑byte header (TEL#3) leak enough state, the whole thing is decryptable from the pcap alone.

Triage

The 116 MB is a .NET single‑file bundle: PE sections ≈ 15 MB, the rest is the embedded runtime + assemblies (bundle signature 8b 12 02 b9 …). Extracting ThreatInvaders.dll (100 KB) and decompiling (ICSharpCode.Decompiler 11.1) yields a normal Space Invaders plus a REST high‑score client.

The telemetry (managed view — the decoy)

TelemetryReporter.BuildDocument builds {request_id, session_id, games_played, client_version, feedback_b64, feedback_length} where:

length      = Math.Min(feedback.Length, 4096);   // capped at 4096
Array.Copy(feedback, buf4096, length);
feedbackB64 = EncodeFeedbackBuffer(buf4096, ref length); // Base64(buf), never edits length
FeedbackLength = length;                          // <= 4096

The raw IL (verified with ilspycmd -il) matches exactly. Yet the pcap shows feedback_length = 0, 0, 8208, 16914, 16430 and high‑entropy feedback_b64 content — impossible under this IL.

Ground‑truth pcap telemetry (note: the telemetry POSTs are LSO/GRO frames with IP total‑length = 0, so reassembly must read to the end of the captured frame, not ip.len):

beacon feedback_length content (Base64‑decoded, nonzero prefix)
TEL#1 0 empty
TEL#2 0 Crashes sometimes. But overall very fun… (plaintext user feedback)
TEL#3 8208 16 bytes (header)
TEL#4 16914 530 bytes (encrypted)
TEL#5 16430 46 bytes (encrypted — flag‑sized)

Proving it's native

  • The extracted game IL is faithful (BuildDocument, EncodeFeedbackBuffer, Math.Min all verified via live JIT dumps).
  • Every managed runtime assembly in the bundle (System.Private.CoreLib.dll, System.Text.Json.dll, …) is byte‑identical to stock .NET 10.0.11 → nothing modified in managed land.
  • The native CoreCLR is a custom build (only ~8 % of 16‑byte code slices match stock) → the modification is native.

Finding the modification (native RE)

Static diffing was hopeless (custom build). Instead: 1. EventPipe rundown (custom eptrace tool) → native code addresses of all JIT'd methods; ReadProcessMemory to dump them. Confirmed BuildDocument/EncodeFeedbackBuffer/Math.Min are faithful. 2. Resolved the actual EncodeFeedbackBuffer call target from BuildDocument's JIT'd code → it lands not on the real method but on an injected function at RVA 0xC6BA0 inside the exe's .text. 3. The bigint type

cert  := 0x00                                    -- leaf: the prime 2 (must be exactly 1 byte)

  • The crux bug: it encoded the prime-2 leaf as a 14-byte 0x01-node 01 00000000 01000000 02 00000000 (a childless node with key=2 and an empty value field) instead of the canonical single 0x00 byte. But it made the cert 6,699 bytes instead of 3,891, with a different SHA-256, so the flag key was always wrong.
  • Because the 0x01-node form carries a value field the verifier ignores, the session concluded there were "216 free leaf-value bytes" and spent enormous effort — a validated SHA-NI brute over the entire uniform 4-byte space, ~50 deterministic value conventions, modexp-residue analysis, and full state-coverage instrumentation — hunting a SHA-256 preimage that never existed. With the correct 0x00 leaf there is no free field at all; the certificate is unique and deterministic.
  • Lesson: "passes the checker" ≠ "canonical." When a downstream step hashes the raw input bytes, a lenient parser that accepts multiple encodings of the same value will happily verify a non-canonical input that then hashes wrong. Re-read the grammar for the minimal/expected encoding of every terminal (here: the leaf is literally one 0x00 byte), don't just find an accepted encoding.

  4. The dqᵢ are randomly scaled, so the gate only passes when every sin is 1: (Kᵢ ± tᵢ) ≡ 90 (mod 360). Each lap has exactly one solution in 0..255, and the 28 solutions spell the flag.

The "statistical mirage" is that the finish line is real, but the only winning run needs 28 laps of 82 s, 51 s, 95 s, … each to the exact second.

Method

I followed the playbook from mahaloz/ilio-mini skills/, analysed remotely without cloning. - flareon: recon → find the check → pull out the constants → cheapest solve (Python, then z3, then emulation) → verify. Flags are usually decrypted at runtime, so capture them rather than reversing everything. - explore-alternatives: when stuck or after a wrong answer, switch to a different line of attack (dynamic, static deep-dive, formats, math, re-read the prompt). - windows-dynamic: adapted here as WSL Ubuntu + WSLg + gdb/gcore instead of wine.

In practice: - Recon (static): it's a Rust/Tauri/V8 binary. - Dynamic: ran it in WSL and read the game script out of a memory dump. - Static deep-dive: after the wrong submission, reversed the Rust builtin hooks. - Math: turned the gate into one equation per lap. - Emulation: unicorn pulled the per-lap constants out of the obfuscated helpers.

Layer 1 — recon

  • It's a 21 MB PIE, stripped. Byte greps show rustc, webkit/gtk, __TAURI, rusty_v8-0.32.1 and V8 9.5.172.19. The 5 \0asm hits are false positives in .text.
  • The Tauri asset table holds 5 brotli-compressed files: index.html, car.png, lap.png, obstacle.png and tree.png.
  • index.html sends {up, down, left, right, restart, bounds} to invoke('plugin:neon|e', …) and renders the {state, obstacles, laps} it gets back. The flag area is #neon-screen, which shows state.neon once state.finished is set.
  • Game keys such as carRatio and totalLaps don't appear anywhere in the file, so the game script is packed. Attempt 1 found the packing: XOR d35a + LZSS + zstd + raw deflate, decoded at runtime.

Layer 2 — the game script (dynamic)

The binary runs in WSL Ubuntu (libwebkit2gtk-4.1 plus WSLg). To get the script out: 1. Set ptrace_scope=0. 2. Launch the game detached and gcore it after about 12 s. The dump is ~15 GB because of the V8 reservation. 3. Grep the dump for carRatio.

The plaintext script (4,229 B) is in the V8 heap and is saved as game.js.

  • Physics:
  • Each frame: speed += 0.5 while holding up, then speed ×= 0.96.
  • There are 28 randomly placed lap lines, the last at y = −100000.
  • Obstacles take the lap-line gaps into account.
  • You crash if you leave input.bounds or come within 32 px of an obstacle. Both checks use the bounds the client sends.
  • Lap bookkeeping: on each lap line the script calls state.bestLapSeconds = Math.min(state.bestLapSeconds, lapSecs), then appends messages[⌊i/2⌋][map[i]] to neon.
  • Finish: neon += String.fromCharCode(64,102,49,97,114,101,45,111,110,46,99,111,109) (= @f1are-on.com, with a digit one), then state.neon = neon.replaceAll(" ","_").

solve.py reproduces the decoy, decode_this_system_to_win_it@f1are-on.com. The JS never uses the lap times beyond display, which is the hint that the host is watching Math.min.

Layer 3 — the Rust builtin hooks ("rip apart the engine")

The first lead was a unique add byte ptr [rcx+0x1e], 0x3b at 0x67ea68. Index 0x1e is the 1 in f1are, and '1'+0x3b = 'l'. The function containing it reads two global f64 values, G1 @ 0x1438590 and G2 @ 0x1438580. Following the xrefs to them leads to the other two hooks. All three are control-flow-flattened, and every constant is built through bswap/rol/add chains.

Hook Function What it does
Array.sort (on splits.sort, in generateLaps) 0x67deb2 Draws k = round(1 + u·65534), with u from a PCG64-style LCG (0x5851f42d4c957f2d, 0x14057b7ef767814f). Multiplies each of the 28 splits by k and queues them (dqᵢ). Sets G2 = −0.0 + Σdqᵢ and resets G1 and the flag vector.
Math.min (lap time is arg 1) 0x67eb83 Pops dqᵢ and increments the lap index i. t = trunc(lapSecs); it rejects the lap unless t is a whole number in [0, 255], then pushes t as a flag byte. Gets (Kᵢ, sᵢ) = 0x68003e(0x67f9d8(i, 90)), where 90 comes from a flattened byte chain. The angle is θ = (π/180)·(Kᵢ + sᵢ·t) reduced mod 2π with round, and D = 180 is also folded from chains. Then G1 += dqᵢ·sin θ, with sin as a 16-term Taylor series (0x687cff → 0x687d80).
String.replaceAll 0x67e81e Gate: |G1| > 1e-6, |G2| > 1e-6 and |G1 − G2| < 1e-6. If it passes, it copies the flag vector over the start of the result string, then s[0x1e] += 0x3b.

Helper imports resolved through RELATIVE relocations: - 0x13b2840 = round - 0x13b2930 = trunc - 0x13b2a00 = a 128-bit division helper

Why the gate pins every lap

G1 − G2 = Σ dqᵢ·(sin θᵢ − 1). Each term is ≤ 0, and every dqᵢ is a random multiple of a nonzero split. So the only reliable way to reach |G1 − G2| < 1e-6 is sin θᵢ = 1 on every lap:

Kᵢ + sᵢ·tᵢ ≡ 90 (mod 360),   tᵢ ∈ [0, 255]

Layer 4 — solving

emu.py maps the ELF's LOAD segments into unicorn, applies the RELATIVE relocations, and then: - runs the pure byte chain (0x67ed5b..0x67eec7) → 90; - runs the 64-bit chains (0x67ef9f..0x67f8b8) → D = 180 and 16 Taylor terms; - calls 0x67f9d8(i, 90) and then 0x68003e(·) for i = 0..27 → (Kᵢ, sᵢ), for example (168236812, −), (−352168521, +), …

First attempt — what went wrong

Attempt 1 (9-neonoutrun/, Opus 5.5 → 4.8, ~12.9 h, ~1.0 M output tokens) did most of the hard engineering: - got the game running in WSL; - recovered the four-stage script packing; - identified all three builtin hooks and the f1are → flare patch.

It then submitted the decoy. Two mistakes: - It misread the angle as independent of the byte. It modeled the Math.min weight as sin(F(lap)°) with F not depending on the lap time. That made G1 == G2 look "unsatisfiable", so it concluded the gate was the mirage and the JS string was the answer. In fact the angle is Kᵢ ± t, and t is the flag byte. - It ignored the prompt's note. "The victory screen will unlock as a hidden next stage dummy challenge" says the neon/victory text is the dummy. The patch it found only fixes the decoy's domain; the gate decides whether the real bytes replace it.

Attempt 2 also began by trusting attempt 1's memory note and repeated the decoy, which was rejected. After re-reading the note, it traced the gate's data flow from replaceAll → G1/G2 → the two writers. The key checks were: 1. Where each operand of the gate is written. 2. What each operand depends on: the popped dq, the lap byte t, and the per-lap constants. 3. Whether the gate is satisfiable per term, rather than as a whole.

Lesson: when a gate looks impossible, check which inputs you assumed were constant. And don't take a flag from an old note as verified until the platform has accepted it.

Tooling used

  • WSL Ubuntu 26.04 (libwebkit2gtk-4.1, WSLg), gdb/gcore and strace for the dynamic stage. Commands that use $ go in script files, because Git Bash expands $ inside wsl -- bash -c.
  • Python: lief (segments and relocations), capstone (cdis.py, a function disassembler using .eh_frame_hdr bounds; xref.py, a brute-force RIP-relative xref finder), unicorn (emu.py) and brotli.
